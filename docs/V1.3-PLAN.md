# Vibe-Code Engineering v1.3 Plan

## 1. v1.2 Baseline

v1.2.0 added imported verification results for:

- Authentication
- Session
- Authorization
- IDOR/BOLA
- Tenant Isolation

The imported-results path validates schema, namespaces, request budgets, redaction and status consistency. It does not independently prove that the external verification requests occurred.

## 2. Current Verification Boundaries

Directly verified by Vibe-Code when configured and passing:

- Phase 2 static security scanning
- Phase 3A unauthenticated defensive runtime checks
- Optional passive OWASP ZAP baseline
- Accessibility automation
- Performance budget/lab checks

Supported through imported external evidence:

- Authentication
- Session
- Authorization
- IDOR/BOLA
- Tenant Isolation

Imported results are validated for schema, namespaces, request budgets, redaction and status consistency. Vibe-Code does not independently prove that the external verification requests occurred or that the reported responses were observed.

Still not directly executed by Vibe-Code:

- Authentication runtime probing
- Session runtime probing
- Authorization runtime probing
- IDOR/BOLA runtime probing
- Tenant isolation runtime probing
- CSRF behaviour
- Rate limiting
- File access
- Webhooks
- Business logic

## 3. Documentation Consistency

The top-level README, adoption guide, security skill documentation and design documents must accurately distinguish:

1. Native Vibe-Code runtime checks.
2. Imported verification results.
3. Areas that remain NOT VERIFIED when no imported results exist.

No documentation change should claim that imported evidence is independently verified by Vibe-Code.

## 4. Candidate v1.3 Capabilities

### A. Native Authentication / Session / Authorization Runtime Verification

Design and implement bounded runtime checks with explicit safety controls.

Areas:

- Authentication
- Session
- Authorization
- IDOR/BOLA
- Tenant isolation

Requirements:

- No production targets
- Explicit target authorization
- Bounded requests
- No uncontrolled brute force
- No credential values in reports
- Strong redaction
- Explicit actor/resource boundaries
- Deterministic findings and statuses
- Clear evidence limitations

### B. CSRF Runtime Verification

Design and implement bounded checks for configured state-changing endpoints without performing destructive operations.

### C. Rate-Limiting Verification

Design bounded verification of configured authentication or sensitive endpoints without brute force or denial-of-service behaviour.

### D. Additional Application Security Areas

Consider later work for:

- File access
- Webhooks
- Business logic

These require separate threat models and safety rules.

## 6. v1.3 Native Verification Areas

### Authentication

Verify configured authentication behaviour using bounded, explicitly defined scenarios.

Examples of checks to design:

- unauthenticated access to a protected endpoint
- rejected invalid authentication attempt
- successful authentication using an externally controlled test identity
- authenticated access to the intended protected endpoint
- logout invalidation where supported

The design must define how sensitive identity material is supplied without storing or reporting credentials.

### Session

Verify configured session behaviour.

Examples:

- session establishment
- session continuity
- session renewal/rotation where supported
- logout invalidation
- session-cookie security observations
- separation between independent test actors

### Authorization

Verify that configured actors receive the expected authorization result.

Examples:

- low-privilege actor denied from privileged operation
- authorized actor allowed to intended operation
- resource ownership boundaries
- tenant boundaries

### IDOR / BOLA

Verify configured cross-actor resource ownership boundaries.

Requirements:

- explicitly declared actors
- explicitly declared resources
- no resource enumeration
- bounded requests
- no destructive modification
- deterministic finding identifiers

### Tenant Isolation

Verify that one tenant cannot access another tenant's declared resource or operation.

Requirements:

- explicitly declared tenants
- explicitly declared resources
- explicit expected allow/deny result
- bounded requests
- no tenant enumeration

## 7. Safety Requirements

Native v1.3 verification must:

- refuse production targets
- require explicit authorization for non-local targets
- use explicit target allow-lists
- use a hard request budget
- use bounded request timeouts
- avoid brute force
- avoid denial-of-service behaviour
- avoid enumeration
- avoid destructive operations
- avoid uploads
- avoid uncontrolled redirects
- avoid sending credential values into reports
- redact sensitive response/header material
- keep evidence deterministic
- keep target scope explicit
- clearly report verification limitations

A failed safety check must prevent the affected verification from running.

## 8. Credential Handling

Credential values must not be persisted in reports, findings, logs, exceptions or SARIF.

The v1.3 design must define a safe boundary between:

- application-specific test identities
- sensitive authentication material
- the native verification engine
- normalized verification evidence

Credentials must not be accepted as arbitrary finding fields.

The system must never expose authentication material through report generation or diagnostic output.

## 9. Status Model

Native verification will use explicit statuses:

- NOT CONFIGURED
- READY
- EXECUTED
- PASS
- FAIL
- INCOMPLETE
- NOT VERIFIED

A PASS must require sufficient executed evidence.

An ambiguous or incomplete check must not become PASS.

Authentication, Session and Authorization aggregate statuses must preserve the distinction between:

- checks actually executed
- imported evidence
- checks not covered
- checks that could not complete

## 10. Finding Namespaces

Native findings will use the existing runtime naming scheme where applicable:

- RT-AUTH-NNN
- RT-SESSION-NNN
- RT-AUTHZ-NNN
- RT-IDOR-NNN
- RT-TENANT-NNN

Native findings and imported findings must remain distinguishable through their result metadata/source.

No finding may be synthesized merely because an area is NOT VERIFIED.

## 11. Reporting

Native verification results must integrate with:

- Phase 3 JSON report
- Phase 3 Markdown report
- Phase 3 report reader
- Security CI SARIF
- Security CI gate
- Engineering CI summary

Reports must distinguish:

- native runtime verification
- imported verification
- NOT VERIFIED coverage gaps

## 13. Long-Term Security Roadmap

### v1.3

Native Authentication / Session / Authorization runtime verification

Includes:

- Authentication
- Session
- Authorization
- IDOR/BOLA
- Tenant isolation

### v1.4

CSRF runtime verification

Scope:

- configured state-changing endpoints
- CSRF token expectations
- same-origin expectations
- safe non-destructive verification

### v1.5

Rate-limiting verification

Scope:

- configured sensitive endpoints
- bounded attempts
- controlled spacing
- detection of missing or inconsistent rate limiting

Requirements:

- no brute force
- no denial-of-service behaviour
- strict request budgets

### v1.6

File access and Webhook security

File access may cover:

- path traversal
- unauthorized file access
- filesystem boundary checks

Webhook security may cover:

- signature verification
- replay protection
- endpoint exposure
- request validation

Each area requires its own threat model and safety controls.

### v1.7

Business logic security

Potential scope:

- business invariants
- state-transition rules
- authorization requirements
- replay/duplicate conditions
- bounded application-specific scenarios

Business logic verification must be configuration-driven and must not assume that a generic scanner understands application-specific rules.
