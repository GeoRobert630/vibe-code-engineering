# Native CSRF Runtime Verification - Technical Design (v1.4)

**Status: DESIGN ONLY. Nothing in this document is implemented.**
Branch: `v1.4-dev`, based on release `v1.3.0` (commit `4470ecf`).
Reference Plan: [docs/V1.4-CSRF-PLAN.md](V1.4-CSRF-PLAN.md).

---

## 1. Executive Summary & Purpose

The purpose of v1.4 is to introduce bounded, deterministic, safe runtime verification of **Cross-Site Request Forgery (CSRF)** defenses into the Vibe-Code Engineering System.

CSRF attacks exploit ambient credentials (HTTP cookies, HTTP basic auth) automatically attached by user agents when issuing cross-site requests to a target web application. Defensive architectures counter CSRF through three distinct, layered mechanisms:
1. **Anti-CSRF Tokens**: Unpredictable, session-bound secrets required on state-changing requests (synchronizer tokens, double-submit cookies, encrypted tokens).
2. **Server-Side Origin/Referer Inspection**: Server inspects and strictly validates `Origin` and `Referer` headers on incoming state-changing requests against an allowlist of trusted origins.
3. **Browser-Enforced SameSite Cookie Policies**: Browsers withhold cookies on cross-site requests when configured with `SameSite=Lax` or `SameSite=Strict`.

This design establishes native runtime verification to confirm that configured state-changing endpoints enforce server-side CSRF defenses, while cleanly separating server-side acceptance observations from proven browser exploitability.

## 2. Core Architectural Principles & Boundaries

### 2.1 Defense Mechanism Separation
The design strictly separates three distinct defense mechanisms:

| Defense Mechanism | Enforced By | How It Works | How v1.4 Verifies It |
|---|---|---|---|
| **Anti-CSRF Token** | Server | Server requires and cryptographically/statefully validates a secret token per session. | Probes send same-origin and cross-origin requests with missing or invalid tokens (Checks C2, C4). |
| **Origin / Referer Validation** | Server | Server verifies that the `Origin` / `Referer` header matches the application's trusted origin. | Probes send requests with an untrusted origin (`Origin: https://untrusted.invalid`) both with and without tokens (Checks C2, C3). |
| **SameSite Cookie Attribute** | Web Browser (Client) | User agent suppresses cookie transmission on cross-site requests. | **Not verified at runtime by HTTP client.** Evaluated via credential-transmission prerequisites and Session check S5 (`RT-SESSION-004`). |

### 2.2 Server-Side Acceptance vs. Proven Browser Exploitability
> [!IMPORTANT]
> **Executor HTTP Client vs. Real Browser Exploitability Boundary**:
> The Phase 3 runtime executor connects directly over raw TCP/TLS sockets using `http.client`. It is an automated HTTP client, **not a web browser**.
>
> When the executor issues a request with a `Cookie` header, the HTTP socket transmits that cookie manually and unconditionally. Claiming that acceptance of a simple cross-origin POST with a manually attached session cookie proves browser CSRF exploitability overclaims what the raw HTTP executor can prove:
> - A browser only attaches cookies to cross-origin requests if the cookie attributes explicitly permit cross-site transmission (e.g. `SameSite=None; Secure`). Modern browsers default unset cookies to `SameSite=Lax`, and browsers never attach `SameSite=Lax` or `SameSite=Strict` cookies to cross-origin POST submissions.
> - Browsers never attach non-ambient credentials (such as `Authorization: Bearer <token>` or custom headers) to cross-origin HTML form submissions.
> - Browsers mandate CORS preflights (`OPTIONS`) for non-simple request shapes (`application/json`, `PUT`, `PATCH`, custom headers).
>
> **The Model: Distinguishing Acceptance from Exploitability**:
> The design strictly distinguishes:
> - **A. Server-Side Cross-Origin Acceptance under an Ambient-Credential Assumption**: What the raw HTTP executor directly observes during Check C2 (the server processes and accepts a state-changing cross-origin request without an anti-CSRF token when credentials are provided). **Check C2 must always record this server-side observation in execution evidence.**
> - **B. Proven Browser CSRF Exploitability**: Emitting finding **`RT-CSRF-001`** represents proven browser exploitability.
>
> **The Exact RT-CSRF-001 Emission Condition**:
> `RT-CSRF-001` may be emitted **only** when the design has sufficient evidence that:
> 1. **Authentication Mechanism Permits Cross-Origin Transmission**: The authentication mechanism must permit the relevant credential to be transmitted cross-origin in a real browser:
>    - The credential must be ambient (cookies, not Bearer tokens or custom authorization headers); AND
>    - There must be sufficient evidence that the session cookie permits cross-origin transmission (e.g. confirmed `SameSite=None; Secure` from cookie attributes or Session check S5). Cookies configured with `SameSite=Strict` or `SameSite=Lax`, or cookies with unspecified SameSite (which modern browsers treat as Lax), do not transmit cross-origin on POST requests; AND
> 2. **Request Shape is Browser-Dispatchable Cross-Origin**:
>    - Simple cross-origin form POST (`application/x-www-form-urlencoded`, `multipart/form-data`, or `text/plain` with no custom headers); OR
>    - For preflight-requiring requests (`application/json`, `PUT`, `PATCH`, custom headers), CORS preflight verification explicitly confirms that the server permits the attacker origin (`Origin: https://untrusted.invalid` with `Access-Control-Allow-Credentials: true`).
>
> **Suppression Rule, Status Resolution & Limitation Recording**:
> If C2 is accepted by the server but browser credential transmission is **not established** (e.g. Bearer auth in use, cookie has `SameSite=Strict` or `SameSite=Lax`, cookie SameSite is unspecified/unverified, or CORS preflight is not verified for JSON):
> 1. The system must **NOT** emit `RT-CSRF-001`.
> 2. The observed server-side acceptance is recorded in report evidence alongside an explicit execution limitation (e.g. `"Server accepted cross-origin state change without anti-CSRF token under ambient credential assumption, but browser credential transmission is not established; RT-CSRF-001 suppressed"`).
> 3. The final area status becomes **`INCOMPLETE`** (reason: `"server accepted cross-origin state change without token under ambient-credential assumption, but browser exploitability is unproven; cannot pass"`). An accepted negative probe must **NEVER** silently resolve to `PASS`.
>
> This preserves the existing SameSite/browser limitation without introducing browser automation.

### 2.3 Session Isolation from v1.3 Authentication
In v1.3, Authentication checks A5 and A6 test logout and assert post-logout invalidation (`RT-AUTH-003`). Consequently, `user_a`'s session is explicitly logged out and invalidated during the Authentication run.

To prevent CSRF verification from accidentally executing against an invalidated session:
1. CSRF verification executes a **Dedicated CSRF Session Setup (Check C0)** prior to any CSRF checks.
2. **Explicit Login Configuration Source**:
   - Primary: `cfg.authentication.login.path` and `cfg.authentication.login.method`.
   - Explicit Fallback: `cfg.runtime_verification.csrf.session_setup.path` and `method` (default: `"POST"`).
   - If neither configuration exists, CSRF verification immediately reports **`INCOMPLETE`** (reason: `"missing login configuration for CSRF session establishment"`).
3. Using `user_a`'s credentials in `IdentityVault`, C0 issues the login request to establish an isolated session (`csrf_session`).
4. If this login fails, CSRF verification immediately reports **`INCOMPLETE`** (reason: `"CSRF session setup C0 failed: unable to establish fresh session for user_a"`).
5. All subsequent CSRF checks (C1–C4) execute exclusively against `csrf_session`.
6. Upon completion of CSRF verification, `csrf_session` is cleanly discarded from memory.

## 3. Safe Mutation & Request Contract

### 3.1 Non-Destructive Mutation Contract
CSRF verification inherently targets state-changing endpoints (`POST`, `PUT`, `PATCH`). To ensure strict non-destructive operation on target systems:
1. **Synthetic / Test Data Only**: Payloads must use dummy, non-critical test values (e.g. `{"theme": "dark"}` or `{"test_property": "vibe_check"}`).
2. **Idempotent or Safely Reversible**: The state change must be safe to execute multiple times without data loss or administrative disruption.
3. **Explicit Positive Marker**: Target configuration must define an explicit `marker` string expected upon successful execution.
4. **Exclusion of DELETE**: The HTTP `DELETE` method is **strictly excluded** from eligible verification methods. In web browsers, HTML forms cannot send `DELETE`, and `DELETE` operations are inherently destructive, violating the non-destructive testing contract.
5. **Deterministic Cleanup Semantics**:
   - If configured under `csrf.cleanup`, the executor issues exactly 1 cleanup request at the conclusion of the CSRF run to restore initial state.
   - **Cleanup Shape**: Always executed as a **same-origin request** (`Origin: <base_url>`, `Referer: <base_url>/app`), using `csrf_session`, and including the valid anti-CSRF token (if tokens are used in the strategy).
   - **Status Independence**: Cleanup failure does **not** change the final security status of the area (a discovered vulnerability or passed test remains unchanged). If cleanup fails, a warning is recorded in the execution evidence/limitations: `"CSRF cleanup request failed: status {code}"`.
   - **No Finding Generated**: Cleanup requests never generate vulnerability findings.

### 3.2 Request Method Constraints
- Supported: `POST`, `PUT`, `PATCH` (default: `POST`).
- Forbidden: `GET`, `HEAD`, `OPTIONS`, `DELETE`. Configuration parsing raises `ConfigError` if a forbidden method is declared.

### 3.3 Positive Control (C1) Success & Redirect Semantics
Because Phase 3 runs with redirects disabled (`redirects_followed = False`), successful web mutations following the Post/Redirect/Get (PRG) pattern return `302 Found` or `303 See Other`.

C1 evaluates to **PASS** (positive control confirmed) if and only if:
1. **2xx Response (`200..299`)**:
   - Status is in `200..299`; AND
   - If `csrf.marker` is configured, the response body contains `csrf.marker`.
2. **3xx Redirect Response (`302`, `303`)**:
   - A `Location` header is present; AND
   - The `Location` header contains `csrf.marker` (e.g., `Location: /settings?saved=true` matching `marker: "saved=true"`); OR
   - The redirect response body contains `csrf.marker`.
3. **Invalid Redirects**:
   - A redirect to an authentication path (e.g. `Location: /login`, `/auth/signin`) or an error path (e.g. `/error`) is treated as a **failure** of the positive control, even if status is 302.

If C1 does not meet the above criteria, C1 fails -> Status is **`INCOMPLETE`** -> All negative checks C2–C4 are **gated** (skipped) -> Zero findings emitted.

## 4. Supported Token Models, Sources & Transport Locations

The design cleanly separates how tokens are **acquired** from how tokens are **transmitted**:

### 4.1 Token Acquisition Source (`csrf.token_source`) & Request Costs
1. **`none`** (0 requests):
   - Used when `token_strategy: "origin_only"`. No token is fetched or sent.
2. **`session_cookie`** (0 requests):
   - Extracted directly from response cookies received during C0 login (e.g. `XSRF-TOKEN` or cookie named in `csrf.token_source_name`).
3. **`prefetch`** (1 GET request):
   - Fetched via a dedicated GET request to `csrf.token_source_path` (e.g. `GET /api/csrf-token`) immediately after C0. Parsed from the JSON key or body marker specified in `csrf.token_source_marker`.
4. **`page_body`** (1 GET request):
   - Fetched via a dedicated GET request to a declared form/landing page (e.g. `GET /user/settings`) immediately after C0. Extracted via regex from the HTML body (e.g. `<input type="hidden" name="_csrf" value="([^"]+)">` or `<meta name="csrf-token" content="([^"]+)">`).

### 4.2 Token Transport Location (`csrf.token_location`)
- **`header`**: Transmitted as an HTTP header (e.g. `X-CSRF-Token`, `X-XSRF-Token`). Default: `X-CSRF-Token`.
- **`form`**: Transmitted as an encoded form parameter (e.g. `_csrf` or `csrf_token`) in `application/x-www-form-urlencoded`.
- **`json`**: Transmitted as a JSON property (e.g. `{"_csrf": "..."}`) in `application/json`.
- **`double_submit_cookie`**: Cookie value mirrored into the declared header or form parameter.

### 4.3 Secret Protection
Raw anti-CSRF tokens are treated as sensitive secrets:
- Raw token values are stored in `SecretValue` instances within an ephemeral `CsrfContext` in memory.
- Raw token values are **never** stored in the v1.3 `SessionState` metadata model (which only records boolean presence flags).
- In reports, evidence, and logs, tokens are masked using `clean()` and `redact()` as `[REDACTED-CSRF-TOKEN]`.

## 5. Token Strategy Applicability Matrix

The configuration property `csrf.token_strategy` controls the exact execution flow of C1–C4:

| Strategy | Meaning | C1 (Positive Control) | C2 (Core Cross-Origin) | C3 (Origin Defense) | C4 (Token Defense) |
|---|---|---|---|---|---|
| **`token`** (default) | Application relies on anti-CSRF tokens. | Requires valid token; same-origin. | Cross-origin; token omitted; asserts denial. | **Skipped** (unless `origin_validation: true` is explicitly configured). | Same-origin; invalid token; asserts denial. |
| **`origin_only`** | Application relies strictly on server-side Origin/Referer inspection. | **NO token required**; same-origin. | Cross-origin; token omitted; asserts denial by Origin. | **Skipped** (redundant with C2; avoids duplicate probe). | **Skipped** (no token expected or validated). |
| **`both`** | Defense-in-depth: enforces both anti-CSRF tokens and server-side Origin validation. | Requires valid token; same-origin. | Cross-origin; token omitted; asserts denial. | Cross-origin; valid token sent; asserts denial by Origin. | Same-origin; invalid token; asserts denial by Token. |

*Note on `origin_only`*: When `token_strategy: "origin_only"`, C2 already tests a cross-origin request against the endpoint. C3 would simply send the exact same cross-origin request with the exact same payload, testing the exact same Origin filter twice. Therefore, C3 is skipped under `origin_only` to eliminate redundant network probes and preserve budget.

## 6. Numbered Verification Checks (C0–C4)

The execution flow consists of Check C0 (session setup), optional token acquisition, four verification checks (C1–C4), and optional cleanup.

```
┌─────────────────────────────────────────────────────────────────┐
│ C0: Dedicated CSRF Session Setup (POST login_path)              │
└───────────────────────────────┬─────────────────────────────────┘
                                │
┌───────────────────────────────▼─────────────────────────────────┐
│ [Optional] Token Acquisition (GET prefetch or page_body)        │
└───────────────────────────────┬─────────────────────────────────┘
                                │
┌───────────────────────────────▼─────────────────────────────────┐
│ C1: Positive Control Baseline (Same-Origin + Valid Session)     │
└───────────────────────────────┬─────────────────────────────────┘
                                │
                        [ Passes C1? ]
                        ├─── NO ───► Status: INCOMPLETE (Gated)
                        │
                       YES
                        │
┌───────────────────────▼─────────────────────────────────────────┐
│ C2: Cross-Origin Ambient Submission Without Token (Core CSRF)   │
└───────────────────────┬─────────────────────────────────────────┘
                        │
┌───────────────────────▼─────────────────────────────────────────┐
│ C3: Cross-Origin Submission With Valid Token (Origin Defense)   │
└───────────────────────┬─────────────────────────────────────────┘
                        │
┌───────────────────────▼─────────────────────────────────────────┐
│ C4: Same-Origin Submission With Invalid Token (Token Defense)   │
└───────────────────────┬─────────────────────────────────────────┘
                        │
┌───────────────────────▼─────────────────────────────────────────┐
│ [Optional] Cleanup: Same-Origin Reversion Request with Token    │
└─────────────────────────────────────────────────────────────────┘
```

### Check C0: Dedicated CSRF Session Establishment
- **Action**: Issue `POST login_path` using `user_a` credentials from `IdentityVault`.
- **Outcome**: Obtains fresh session cookie/token (`csrf_session`). If `token_source` is `"prefetch"` or `"page_body"`, issues 1 GET request to retrieve initial anti-CSRF token into `SecretValue`.
- **Failure**: If login fails, status becomes `INCOMPLETE`. C1–C4 are not executed.

---

### Check C1: Baseline Legitimate Request (Positive Control)
- **Objective**: Confirm the state-changing endpoint accepts legitimate authenticated requests.
- **Request**:
  - Method: `csrf.method` (`POST`, `PUT`, or `PATCH`).
  - Path: `csrf.path`.
  - Headers:
    - Session cookie (`csrf_session`).
    - Same-origin headers: `Origin: <target_base_url>`, `Referer: <target_base_url>/app`.
    - Content-Type: `csrf.content_type`.
    - Anti-CSRF token: Valid token included if `token_strategy` is `token` or `both`. **Omitted if `token_strategy: "origin_only"`.**
  - Body: `csrf.body`.
- **Expected Outcome**: HTTP `200..299` with body marker, or `302/303` with marker in `Location` or body.
- **Gating Verdict**:
  - **Pass**: Proceeds to C2–C4.
  - **Fail**: Status becomes **`INCOMPLETE`**. C2–C4 are skipped. Zero findings emitted.

---

### Check C2: Cross-Origin Ambient Submission Without Token (Core CSRF Probe)
- **Objective**: Test whether the application accepts cross-origin requests when ambient credentials are sent without an anti-CSRF token.
- **Attacker Threat Model**: A third-party malicious website (`https://untrusted.invalid`) tricks the victim's browser into submitting a cross-site form or request with ambient cookies. The attacker cannot read the victim's anti-CSRF token under the Same-Origin Policy.
- **Request**:
  - Method: `csrf.method`.
  - Path: `csrf.path`.
  - Headers:
    - Session cookie (`csrf_session`).
    - Cross-origin headers: `Origin: https://untrusted.invalid`, `Referer: https://untrusted.invalid/exploit.html`.
    - Anti-CSRF token: **Omitted** (none).
  - Body: `csrf.body`.
- **Expected Outcome**: Request must be denied (`400`, `403`, `422`, or in `deny_statuses`).
  - **C2 Rejected**: Negative check passed. Proceed to subsequent checks.
  - **C2 Accepted AND Browser CSRF Exploitability is Proven**:
    - Emits finding **`RT-CSRF-001`** (Core CSRF vulnerability, `Severity: HIGH`, `Confidence: HIGH`).
    - Status resolves to **`FAIL`**.
  - **C2 Accepted BUT Browser CSRF Exploitability is NOT Established**:
    - Status resolves to **`INCOMPLETE`** (reason: `"server accepted cross-origin state change without token under ambient-credential assumption, but browser credential transmission is not established; verification incomplete"`).
    - Do **NOT** emit `RT-CSRF-001`.
    - Preserve server-side acceptance evidence and the explicit limitation.
    - Negative check did NOT pass (server accepted mutation); it must **NEVER** silently resolve to `PASS`.

---

### Check C3: Cross-Origin Submission With Valid Token (Isolates Server-Side Origin Defense)
- **Objective**: Test whether the server validates `Origin` / `Referer` headers when a valid token is present.
- **Attacker Threat Model**: Simulates scenarios where an attacker bypasses token isolation (e.g. cross-subdomain token leak, double-submit cookie injection, or shared domain token pool), or tests compliance when the application declares server-side Origin checking as an explicit defensive layer.
- **Applicability**: Executed ONLY when `csrf.token_strategy: "both"` OR (`csrf.token_strategy: "token"` AND `csrf.origin_validation: true`). May use JSON or custom headers as configured. (Skipped in `origin_only` to prevent duplicate probe, and skipped in `token` when origin validation is not declared).
- **Request**:
  - Method: `csrf.method`.
  - Path: `csrf.path`.
  - Headers:
    - Session cookie (`csrf_session`).
    - Cross-origin headers: `Origin: https://untrusted.invalid`, `Referer: https://untrusted.invalid/exploit.html`.
    - Anti-CSRF token: **Valid** anti-CSRF token included.
  - Body: `csrf.body`.
- **Expected Outcome**: Server must reject the request due to untrusted origin (`400`, `403`, `422`, or in `deny_statuses`).
  - **C3 Rejected**: Negative check passed.
  - **C3 Accepted**: Server accepted request with untrusted Origin header despite configured Origin defense.
    - Emits finding **`RT-CSRF-003`** (Origin policy violation, `Severity: MEDIUM`, `Confidence: HIGH`).
    - Status resolves to **`FAIL`**.
  - **C3 Ambiguous or Unverified**: If the server returns an ambiguous status or accepted-but-not-provable result, do **NOT** emit finding; status resolves to **`INCOMPLETE`** (with recorded evidence and explicit limitations). It must **NEVER** silently become `PASS`.

---

### Check C4: Same-Origin Submission With Invalid / Tampered Token (Isolates Token Validation)
- **Objective**: Test whether the server cryptographically or statefully validates the anti-CSRF token value, or merely checks for presence.
- **Applicability**: Executed ONLY when `csrf.token_strategy` is `token` or `both`. May use JSON or custom headers as configured. (Skipped if `token_strategy: "origin_only"`).
- **Request**:
  - Method: `csrf.method`.
  - Path: `csrf.path`.
  - Headers:
    - Session cookie (`csrf_session`).
    - Same-origin headers: `Origin: <target_base_url>`, `Referer: <target_base_url>/app`.
    - Anti-CSRF token: **Invalid / Tampered** (`"vibe_invalid_csrf_token_value_0000"`).
  - Body: `csrf.body`.
- **Expected Outcome**: Server must reject the invalid token (`400`, `403`, `422`, or in `deny_statuses`).
  - **C4 Rejected**: Negative check passed.
  - **C4 Accepted**: Server accepted request with invalid / tampered token.
    - Emits finding **`RT-CSRF-002`** (Token defense failure, `Severity: HIGH`, `Confidence: HIGH`).
    - Status resolves to **`FAIL`**.
  - **C4 Ambiguous or Unverified**: If the server returns an ambiguous status or accepted-but-not-provable result, do **NOT** emit finding; status resolves to **`INCOMPLETE`** (with recorded evidence and explicit limitations). It must **NEVER** silently become `PASS`.

## 7. Status Precedence & Semantics

The status semantics for CSRF are strictly defined to eliminate any ambiguity:

- **`csrf` absent** -> **`NOT CONFIGURED`**: `runtime_verification.csrf` is not declared in configuration (0 requests sent; `source: "none"`).
- **`csrf` configured but required login configuration absent** -> **`INCOMPLETE`**: `runtime_verification.csrf` is declared, but neither canonical login configuration (`cfg.authentication.login`) nor dedicated session setup (`csrf.session_setup`) is provided, or required identity credentials are missing (reason: `"missing login configuration for CSRF session establishment"`).
- **C0 login attempted and failed** -> **`INCOMPLETE`**: Dedicated session establishment was attempted but failed due to network error, 4xx/5xx status, or invalid credentials (reason: `"CSRF session setup C0 failed: unable to establish fresh session for user_a"`).
- **Positive Control C1 failed** -> **`INCOMPLETE`**: Target unreachable, marker missing, 500 error, or unexpected redirect. Negative checks C2–C4 are gated; zero findings emitted.
- **C2 accepted BUT browser CSRF exploitability NOT established** -> **`INCOMPLETE`**: Server accepted state change without token under ambient-credential assumption, but cross-origin credential transmission could not be proven. RT-CSRF-001 is suppressed, server-side observation is preserved with explicit limitation, and area resolves to INCOMPLETE (cannot pass).
- **C3 / C4 ambiguous, unverified, or accepted-but-unproven** -> **`INCOMPLETE`**: Server returned an ambiguous status or accepted under unverified conditions where a finding is unprovable. Does not emit finding; resolves to INCOMPLETE (cannot pass).
- **Any negative check failed & finding emitted** -> **`FAIL`**: Emits at least one `RT-CSRF-*` finding (`RT-CSRF-001`, `RT-CSRF-002`, or `RT-CSRF-003`).
- **All applicable negative probes actually rejected** -> **`PASS`**: Requires C1 success, every applicable negative probe actually rejected by server, 0 findings, and no accepted negative probe remaining unresolved or suppressed.
- **Neither native nor imported CSRF verification configured** -> **`NOT VERIFIED`**: When evaluating the overall verification summary / multi-area reader, if neither native `runtime_verification.csrf` nor imported `verification_results.areas.csrf` is present, the area reports `NOT VERIFIED` (`source: "none"`).

The deterministic runtime status precedence for native execution is:

```
┌────────────────────────────────────────────────────────────────────────┐
│ 1. runtime_verification.csrf absent? ──────────► NOT CONFIGURED        │
│ 2. Pre-execution safety refusal/overbudget? ───► INCOMPLETE (refused)  │
│ 3. CSRF configured but login config absent? ───► INCOMPLETE (config)   │
│ 4. Dedicated C0 Login attempted & failed? ─────► INCOMPLETE (gated)    │
│ 5. Positive Control C1 failed? ────────────────► INCOMPLETE (gated)    │
│ 6. Any negative check failed & finding emitted?► FAIL (finding)        │
│ 7. Any negative check accepted-but-unproven                            │
│    or ambiguous? ──────────────────────────────► INCOMPLETE (unproven) │
│ 8. C1 succeeded, EVERY applicable negative                             │
│    probe ACTUALLY rejected, zero findings? ────► PASS                  │
│                                                                        │
│ * Multi-area reader rule:                                              │
│   Neither native nor imported CSRF configured ─► NOT VERIFIED (none)   │
└────────────────────────────────────────────────────────────────────────┘
```

1. **`NOT CONFIGURED`**: `runtime_verification.csrf` is absent from configuration. (0 requests sent, `source: "none"`).
2. **`INCOMPLETE` (Refused)**: Safety gate refusal or plan over-budget before execution.
3. **`INCOMPLETE` (Configuration Gap)**: `runtime_verification.csrf` is configured, but required login configuration (`cfg.authentication.login` or `csrf.session_setup`) is absent.
4. **`INCOMPLETE` (Execution Gated)**:
   - C0 login failed (unable to establish fresh session);
   - Positive control C1 failed (target unreachable, marker missing, error response);
   - Target timed out or connection errored.
   *Gating rule*: Negative checks C2–C4 are not run; zero findings emitted.
5. **`READY`**: Used only in `--plan` mode: plan built and budgeted, no requests sent.
6. **`EXECUTED`**: Internal execution pipeline status before final status resolution.
7. **`FAIL`**: One or more negative checks failed and met finding emission criteria, emitting at least one `RT-CSRF-*` finding (`RT-CSRF-001`, `RT-CSRF-002`, or `RT-CSRF-003`).
8. **`INCOMPLETE` (Unresolved / Unproven Negative Probe)**:
   - C2 accepted but browser CSRF exploitability is NOT established: Server accepted cross-origin state change without token under ambient-credential assumption, but browser credential transmission is not proven. Do NOT emit `RT-CSRF-001`; record server-side acceptance evidence and explicit limitation; area status resolves to **`INCOMPLETE`** (reason: `"server accepted cross-origin state change without token under ambient-credential assumption, but browser credential transmission is not established; cannot pass"`).
   - C3 or C4 ambiguous or accepted-but-unproven result: If C3 or C4 produces an ambiguous response, network anomaly, or accepted-but-not-provable negative result, do NOT emit finding; area status resolves to **`INCOMPLETE`** (reason: `"negative check produced an ambiguous or unverified result; cannot pass"`).
   - Ambiguous, unverified, or accepted-but-not-provable negative results must **NEVER** silently become `PASS`.
9. **`PASS`**: Strict criteria. PASS requires:
   - Positive control C1 succeeded;
   - Every applicable negative probe (C2, C3 if applicable, C4 if applicable) was **actually rejected** by the target server;
   - Zero findings emitted;
   - **No accepted negative probe remains unresolved or suppressed**.
10. **`NOT VERIFIED`**: In multi-area reporting / readers, applied when neither native verification nor imported results are configured for CSRF (`source: "none"`).

## 8. Native vs. Imported Verification Coexistence

### 8.1 Source Exclusivity & Precedence
In strict accordance with the v1.3 source model ([docs/V1.3-AUTH-SESSION-AUTHORIZATION-DESIGN.md](V1.3-AUTH-SESSION-AUTHORIZATION-DESIGN.md) §2):
- **Conflict Refusal**: Configuring native verification (`runtime_verification.csrf`) AND imported results (`verification_results.areas.csrf`) simultaneously for the `csrf` area is a **configuration error**, refused by `config.py` before any network request is issued.
- **Individual Area Source**: The `csrf` area has exactly one source: `native`, `imported`, or `none`.
  - If verified natively: `source: "native"`. Findings carry `origin: "native-verification"`.
  - If loaded from import: `source: "imported"`. Findings carry `origin: "imported-verification"`.
  - If unconfigured: `source: "none"`.
- **Aggregate Summary Integration**:
  - In `engineering-summary.json`, `verification_source.csrf` reports `"native"`, `"imported"`, or `"none"`.
  - `mixed` is never applied to the individual `csrf` area (only valid on the aggregate `authorization` block across its 3 sub-areas).

## 9. Request Budget Specifications

### 9.1 Exact Operation Breakdown
Every possible request is accounted for mathematically:

| Operation | Condition | Request Count |
|---|---|---|
| C0: Dedicated Login | Required when CSRF configured | 1 |
| Token Acquisition | Optional: when `token_source` is `prefetch` or `page_body` | 1 |
| C1: Positive Control | Required | 1 |
| C2: Core Cross-Origin Probe | Required | 1 |
| C3: Origin Defense Probe | Applicable under `both` or `token + origin_validation` | 1 |
| C4: Token Defense Probe | Applicable under `token` or `both` | 1 |
| Cleanup Request | Optional: when `csrf.cleanup` is configured | 1 |

$$\text{Maximum Possible CSRF Requests} = 1 + 1 + 1 + 1 + 1 + 1 + 1 = 7$$

- **CSRF Area Hard Maximum (`AREA_HARD_MAXIMUMS["csrf"]`)**: **7 requests**.

### 9.2 Overall Native Request Ceilings
In v1.3:
- Auth: 9, Session: 1, Authz: 2, IDOR: 4, Tenant: 4 = 20 total.
- `FIXTURE_MAX_REQUESTS` = 20, `LOCAL_APP_MAX_REQUESTS` = 21.

In v1.4:
- With CSRF added (up to 7 requests):
  - `FIXTURE_MAX_REQUESTS`: **27 requests** (`20 + 7`).
  - `LOCAL_APP_MAX_REQUESTS`: **28 requests** (`21 + 7`, includes 1 identity setup request).
- Plans are strictly validated prior to execution: if planned requests exceed these caps, execution is refused (`INCOMPLETE`).

## 10. Schema 1.1 Specification & Backward Compatibility

### 10.1 Schema Dual-Version Validator Contract
The verification results loader and validator (`runtime_security.verification.importer`) supports both Schema 1.0 and Schema 1.1:
1. **Schema 1.0 Documents**:
   - Files declaring `"schema_version": "1.0"` are validated against Schema 1.0.
   - The total requests count must be `<= 20`.
   - The five v1.2/v1.3 areas (`authentication`, `session`, `authorization`, `idor_bola`, `tenant_isolation`) are accepted.
   - `csrf` is absent and reports `NOT VERIFIED` (`source: "none"`).
2. **Schema 1.1 Documents**:
   - Files declaring `"schema_version": "1.1"` are validated against Schema 1.1.
   - Adds optional `csrf` under `properties.areas`:
     ```json
     "csrf": {
       "$ref": "#/$defs/area",
       "description": "Findings RT-CSRF-NNN only."
     }
     ```
   - Maximum imported `requests_count` in Schema 1.1 is 27 total.
   - If `csrf` is omitted from a Schema 1.1 file, it cleanly defaults to `NOT VERIFIED` (`source: "none"`).

## 11. Configuration Schema (`runtime_verification.csrf`)

```yaml
runtime_verification:
  mode: fixture  # or local-app
  allowed_targets:
    - "http://127.0.0.1:8080"
  actors:
    user_a: { role: user }
  routes:
    protected: { path: /api/profile, marker: "profile_data" }

  csrf:
    path: /api/user/settings                # Required: Relative path starting with /
    method: POST                            # Optional: POST | PUT | PATCH (default: POST)
    marker: "saved"                         # Required: Expected success marker
    content_type: json                      # Optional: json | form (default: json)
    body: '{"theme":"dark"}'                # Optional: Synthetic non-destructive body
    token_strategy: token                   # Optional: token | origin_only | both (default: token)
    token_source: none                      # Optional: none | session_cookie | prefetch | page_body
    token_source_path: /api/csrf-token      # Optional: Path for prefetch or page_body GET
    token_source_marker: "token"            # Optional: Key for prefetch token
    token_location: header                  # Optional: header | form | json | double_submit_cookie
    token_name: X-CSRF-Token                # Optional: Header or parameter name
    origin_validation: false                # Optional: boolean, enable C3 origin check
    session_setup:                          # Optional: Explicit login if cfg.authentication.login absent
      path: /custom/login
      method: POST
    cleanup:                                # Optional: Same-origin reversion mutation
      method: POST
      body: '{"theme":"light"}'
```
