## 2. Implementation Work Packages

### Package A: Acceptance Contracts (Test-First Scaffold)
Before writing implementation code, create dedicated v1.4 acceptance test files marked with `pytest.mark.xfail(strict=True)`:

1. `tools/phase3-runtime-security/tests/test_v14_csrf_config.py`:
   - Validates `runtime_verification.csrf` config parsing.
   - Asserts rejection of credential-shaped keys, invalid HTTP methods (`GET`, `HEAD`, `OPTIONS`, `DELETE`), and absolute URLs.
   - Validates token strategies (`token`, `origin_only`, `both`), token locations (`header`, `form`, `json`, `double_submit_cookie`), and token sources (`none`, `session_cookie`, `prefetch`, `page_body`).
2. `tools/phase3-runtime-security/tests/test_v14_csrf_plan.py`:
   - Asserts plan creation for C0–C4 when `csrf` is configured.
   - Asserts budget enforcement (up to 7 requests planned, hard maximum 7).
   - Asserts `NOT CONFIGURED` when `csrf` is absent from config.
3. `tools/phase3-runtime-security/tests/test_v14_csrf_native.py`:
   - Validates execution against mock server / fixture:
     - **Session Isolation**: Proves C0 establishes fresh `csrf_session` using canonical `cfg.authentication.login.path` or `csrf.session_setup` and does not fail even if A5/A6 previously logged out `user_a`.
     - **C1 Positive Control**: Validates 2xx with marker and 302/303 with marker in `Location`/body; asserts that C1 failure gates C2–C4 and yields `INCOMPLETE` with zero findings. Proves `origin_only` does not require tokens in C1.
     - **C2 Core CSRF & Browser Exploitability Gating**:
       - C2 always records server-side cross-origin acceptance under an ambient-credential assumption.
       - Emits RT-CSRF-001 (Confidence: HIGH) only when sufficient evidence confirms that the authentication mechanism permits the relevant credential to be transmitted cross-origin in a real browser (ambient cookie auth with confirmed cross-origin transmission, e.g. SameSite=None; Secure) and request is browser-dispatchable (simple form POST or verified permissive CORS preflight).
        - Proves that when browser credential transmission is not established (e.g. cookie has SameSite=Strict or SameSite=Lax, default/unverified SameSite, or auth is Bearer token), server-side acceptance does **NOT** emit RT-CSRF-001, records server-side acceptance evidence and an explicit limitation instead, and the final status resolves to INCOMPLETE (never PASS).
       - Proves JSON / PUT / PATCH accepted without token does **NOT** emit RT-CSRF-001 unless CORS preflight explicitly permits attacker origin with credentials.
      - **C3 Origin Defense**: Proves cross-origin submission with valid token accepted when origin_validation: true -> RT-CSRF-003 (Origin policy violation). Proves C3 is skipped in origin_only. Proves ambiguous or unverified C3 response yields INCOMPLETE (never PASS).
      - **C4 Token Defense**: Proves same-origin submission with invalid/tampered token accepted -> RT-CSRF-002 (Token defense bypass). Proves C4 is skipped in origin_only. Proves ambiguous or unverified C4 response yields INCOMPLETE (never PASS).
     - **Origin-Only Architecture**: Proves endpoint with `token_strategy: "origin_only"` passes when C2 rejected, without requiring tokens.
     - **Secret Handling**: Proves raw tokens are held in `SecretValue` / `CsrfContext` and never stored in `SessionState`.
     - **Cleanup Semantics**: Proves optional cleanup is sent same-origin with valid token, and failure does not change security outcome.
4. `tools/security-ci/tests/test_v14_csrf_security_ci.py`:
   - Asserts Security CI recognizes `csrf` area and enforces gating on `FAIL` or `INCOMPLETE`.
   - Asserts SARIF generation maps `RT-CSRF-*` findings with `origin: "native-verification"`.
5. `tools/engineering-ci/tests/test_v14_csrf_engineering_contract.py`:
   - Asserts Engineering CI summarizes `csrf` status and records source (`native`, `imported`, or `none`).
6. `tools/phase3-runtime-security/tests/test_v14_import_schema11.py`:
   - Validates Schema 1.1 accepting `csrf` in imported verification files (up to 27 requests).
   - Validates Schema 1.0 backward compatibility (older files declaring schema 1.0 continue to validate under 20 request limit and report `NOT VERIFIED`).

### Package C: Native CSRF Module
Target file: `tools/phase3-runtime-security/src/runtime_security/native/csrf.py`
- Define constants:
  - `CSRF_NAMESPACE = "RT-CSRF-*"`
  - `UNTRUSTED_ORIGIN = "https://untrusted.invalid"`
  - `INVALID_TOKEN_VALUE = "vibe_invalid_csrf_token_value_0000"`
- Implement ephemeral context & functions:
  - `CsrfContext`: In-memory container holding session reference and `SecretValue` token.
  - `build_csrf_requests(cfg: Config) -> list[PlannedRequest]`: Constructs C0–C4 request descriptors according to the strategy applicability matrix.
  - `evaluate_csrf_checks(...) -> tuple[str, list[Finding], list[dict]]`: Classifies responses, validates positive control gating, enforces browser exploitability gating for C2 / `RT-CSRF-001`, evaluates C2/C3/C4 independently, and emits findings.
  - `make_csrf_finding(finding_id: str, ...) -> Finding`: Instantiates findings for `RT-CSRF-001`, `RT-CSRF-002`, `RT-CSRF-003`.

   - CSRF execution never exceeds 7 requests. Total run never exceeds 27 requests (fixture) or 28 requests (local-app).
4. **Secret Hygiene**:
   - No CSRF token or session credentials logged or leaked unredacted. Raw tokens kept in `SecretValue` only.
5. **Clean Verification**:
   - `git diff --check` clean.
   - All caches (`__pycache__`, `.pytest_cache`) deleted prior to final sign-off.
