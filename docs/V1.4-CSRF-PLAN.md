# Vibe-Code Engineering v1.4 Plan: CSRF Runtime Verification (Final Revision)

## 1. Context and Baseline

The Vibe-Code Engineering System reached **v1.3.0** (commit `4470ecf`), which established native runtime verification for five core security areas:
1. **Authentication (A1–A6)**: Validated login, unauthenticated rejection, invalid credentials rejection, malformed payload rejection, logout, and post-logout session invalidation (`RT-AUTH-001` .. `RT-AUTH-003`).
2. **Session (S1–S6)**: Validated session establishment, continuity across requests, token fixation rotation across login (`RT-SESSION-001`), and cookie defensive flags (`RT-SESSION-002` HttpOnly, `RT-SESSION-003` Secure, `RT-SESSION-004` SameSite).
3. **Authorization (Z1–Z2)**: Validated vertical access control against privileged administrative endpoints (`RT-AUTHZ-001`).
4. **IDOR/BOLA (I1–I4)**: Validated horizontal access control against object ownership across distinct users (`RT-IDOR-001`).
5. **Tenant Isolation (T1–T4)**: Validated strict boundary separation across multi-tenant resources (`RT-TENANT-001`).

In v1.3, CSRF verification was explicitly deferred to **v1.4**. The v1.3 architecture is frozen; v1.4 introduces CSRF runtime verification while preserving complete backwards compatibility with v1.2 and v1.3.

## 2. v1.4 Objectives & Architectural Principles

### 2.1 Core Objective
Provide bounded, deterministic, safe runtime verification of Cross-Site Request Forgery (CSRF) defenses for web applications and APIs operating in local environments (`fixture` and `local-app` modes).

### 2.2 Key Architectural Principles
1. **Server-Side Acceptance vs. Proven Browser Exploitability**:
   - Strictly distinguishes server-side cross-origin acceptance under an ambient-credential assumption (recorded as execution evidence) from proven browser CSRF exploitability (`RT-CSRF-001`).
   - Check C2 must always record the server-side observation.
   - `RT-CSRF-001` may be emitted only when the design has sufficient evidence that the authentication mechanism permits the relevant credential to be transmitted cross-origin (ambient cookie auth with verified cross-origin transmission, e.g. confirmed `SameSite=None; Secure`) and the request is browser-dispatchable (simple form POST or verified permissive CORS preflight).
   - If browser credential transmission is not established (Bearer tokens, confirmed `SameSite=Strict` or `SameSite=Lax`, default/unverified SameSite), `RT-CSRF-001` is NOT emitted. The observed server-side acceptance and an explicit limitation are recorded, and the area resolves to **`INCOMPLETE`** (cannot pass).
2. **Independent Defense Isolation & Strategy Matrix**:
   - Distinctly isolates **anti-CSRF token verification** from **server-side Origin/Referer inspection** and **browser-enforced SameSite cookie behavior**.
   - Supports explicit token strategies: `token`, `origin_only`, and `both`.
   - In `origin_only` mode, endpoints are not penalized or failed for lacking tokens, provided cross-origin requests are rejected.
3. **Dedicated CSRF Session Setup (Check C0)**:
   - CSRF runtime verification establishes its own fresh, dedicated session (`csrf_session`) via a dedicated login request prior to C1–C4.
   - C0 obtains login parameters from `cfg.authentication.login` or explicit `csrf.session_setup` (no hard-coded paths).
   - Completely prevents accidental reuse of a session invalidated by v1.3 A5/A6 logout checks.
4. **Unambiguous Status Semantics**:
   - `csrf` absent -> `NOT CONFIGURED`
   - `csrf` configured but required login configuration absent -> `INCOMPLETE`
   - C0 login attempted and failed -> `INCOMPLETE`
   - Positive control C1 failed -> `INCOMPLETE`
   - C2 accepted but browser exploitability not established -> `INCOMPLETE` (RT-CSRF-001 suppressed, acceptance recorded with limitation)
   - C3 / C4 ambiguous or accepted-but-unproven -> `INCOMPLETE` (never silently PASS)
   - Any negative check failed & finding emitted -> `FAIL`
   - PASS requires: C1 succeeded, every applicable negative probe was actually rejected, zero findings, and no accepted negative probe remains unresolved or suppressed
   - Neither native nor imported CSRF verification configured -> `NOT VERIFIED`
5. **Safe Mutation Contract & Method Restrictions**:
   - Only `POST`, `PUT`, and `PATCH` are eligible. `DELETE` is strictly excluded to prevent destructive mutations.
   - Payloads are synthetic and non-critical, requiring explicit success markers, with optional deterministic same-origin cleanup.
6. **Exact Request Budgets**:
   - CSRF Area Hard Maximum: **7 requests** (C0 login, optional token acquisition, C1 positive control, C2 core CSRF, C3 origin defense, C4 token defense, optional cleanup).
   - Overall native verification maximum: **27 requests** in `fixture` mode (v1.3 20 + 7) and **28 requests** in `local-app` mode (v1.3 21 + 7).
7. **Dual-Version Schema Importer**:
   - Importer accepts both Schema 1.0 (20 request cap, 5 areas) and Schema 1.1 (27 request cap, optional 6th `csrf` area).

## 4. Implementation Phasing

- **Phase 1: Design & Acceptance Contracts (Current)**
  - Technical Design: `docs/V1.4-CSRF-DESIGN.md`.
  - Implementation Handoff: `docs/V1.4-IMPLEMENTATION-HANDOFF.md`.
  - Acceptance contract test suites (`test_v14_*.py`) with strict `xfail` markers.
- **Phase 2: Configuration & Planning**
  - Add `runtime_verification.csrf` schema and parser in `config.py`.
  - Implement `plan.py` additions for CSRF checks C0–C4 and request budget validation (hard maximum 7).
- **Phase 3: Core CSRF Execution & Classification**
  - Create `tools/phase3-runtime-security/src/runtime_security/native/csrf.py`.
  - Implement session isolation login (C0) using canonical auth config and C1 positive control gating.
  - Implement browser-exploitability gating for C2 / `RT-CSRF-001`.
  - Implement deterministic finding emission for `RT-CSRF-001`, `RT-CSRF-002`, `RT-CSRF-003`.
- **Phase 4: Reporting & CI Synchronization**
  - Wire CSRF into Phase 3 JSON/Markdown reporting and CLI reader.
  - Update Security CI inputs, gate, and SARIF exporter.
  - Update Engineering CI summary extraction.
  - Implement dual-version Schema 1.0 / 1.1 importer.
- **Phase 5: Verification & Release Readiness**
  - Unmark `xfail` tests to `pass`.
  - Run full test matrix across Phase 3, Security CI, and Engineering CI.
  - Conduct final security semantic review and documentation consistency pass.
