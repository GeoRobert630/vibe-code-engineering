## 3. Phase 3 Reporting Work

Contracts: xfails 1 and 2. Existing code to investigate:

- **`tools/phase3-runtime-security/src/runtime_security/verification/report.py`, `area_fields()`:** always sets
  `"source": "imported"` for every area of a configured import, including areas absent from the file. This is the
  cause of xfail 1.
- **`tools/phase3-runtime-security/src/runtime_security/authz/status.py`:**
  - `imported_authz_status()` builds the `authorization` block and its `subareas` for imports. It is where
    `verification_source` / `verification_subarea_source` would be added (xfail 2).
  - `authz_area_status()` and `authz_subareas()` build the block without an import. The design (section 19) keeps
    that block in its v1.2 shape.
- **`tools/phase3-runtime-security/src/runtime_security/auth/status.py`, `auth_area_status()`:** the
  Authentication/Session blocks. The same source rule applies there. Xfail 1 accepts either `source: "none"` or no
  `source` key on `auth_areas.authentication`.
- **`tools/phase3-runtime-security/src/runtime_security/reporting/json_report.py`, `build()`:** wires the blocks into
  the report.

Rules (design sections 2, 16 and 19):

- **Individual sources:** an area or sub-area source is `native`, `imported` or `none`. `none` means no evidence from
  either source.
- **Aggregate `verification_source`:** takes the shared value when all three sub-areas agree, otherwise `mixed`.
  `mixed` never appears as an individual source.
- **`verification_subarea_source`:** always lists `authorization`, `idor_bola` and `tenant_isolation`. Each sub-area
  block's own `source` stays authoritative.
- **Source vs status:** source computation must not read or change status. The existing `verification/status.py`
  `aggregate()` takes statuses only; `test_status_aggregate_takes_no_source_input` pins that.
- **v1.2 shape stays:** without `verification_results` the blocks keep the v1.2 shape.
  `test_no_configuration_reports_no_source` pins "no `source` key" in that case.
- **Imported areas:** areas present in an import keep `source: "imported"`. `test_imported_areas_report_source_imported`
  pins that.

Native evidence (`source: "native"`) cannot be produced yet: there is no native execution (section 8). The source
computation must accept `native` as a value, but no Phase 3 code path emits it at this checkpoint.

## 4. Report Reader Redaction

Contract: xfail 3.

- **Reader:** `skills/06-security/17-security-audit/scripts/read_phase3_report.py`.
  - Its `clean()` only replaces control characters and truncates.
  - `render()` prints `f['title']`, `f['endpoint']`, `f['actual']`/`f['expected']` and `f['evidence']` through that
    `clean()`, so credential-shaped values in the report are printed as they are.
- **Existing redaction:** `tools/phase3-runtime-security/src/runtime_security/utils/redaction.py`, functions `redact()`
  and `clean()`. The stricter layer for imported evidence is
  `tools/phase3-runtime-security/src/runtime_security/verification/redaction.py`, functions `strict_redact()` and
  `strict_clean()`.
- **Requirement:** the reader must redact finding text itself (design section 18: every consumer redacts again, even
  when the upstream report is already redacted), reusing the existing mechanism rather than a second implementation.
- **Open point to investigate:** the reader is a standalone script. It imports only the standard library and does not
  have `runtime_security` on its import path. How it reuses the existing redaction module (package import, path
  setup, or another existing sharing pattern in the repository) is an implementation decision that must not
  duplicate the redaction rules.
- **Test input:** the test's hand-written report (`_hand_written_phase3_report()`) plants fake bearer, cookie and
  query values in `endpoint`, `actual` and `evidence`. None may appear in `render()` output.
- **Must keep passing:** `test_reader_summary_of_generated_report_is_clean` and the existing reader tests in
  `test_verification_import.py`, `test_authz_status.py` and `test_authz_subareas.py`.

## 5. Security CI Work

Contracts: xfails 4-8. Existing code to investigate:

- **`tools/security-ci/src/security_ci/inputs.py`:**
  - `Bundle`: `verification`, `verification_subareas`, `imported_verification` and `incomplete` exist; nothing holds
    native data yet.
  - `_coverage_status()`, the status normalisation.
  - `load_phase3()`: reads `auth_areas`, `authorization` and its `subareas`, and `verification_import`. It adds
    `"phase3 imported verification"` to `bundle.incomplete` for an INCOMPLETE import and sets `extra` on each
    `UnifiedFinding` (RT-AUTHZ metadata, `origin: imported-verification`).
- **`tools/security-ci/src/security_ci/sarif.py`:**
  - `_result()` copies `f.extra` into result properties.
  - `build()` writes the Phase 3 run properties (`verificationStatus`, `verificationSubareas`,
    `importedVerification`).
- **`tools/security-ci/src/security_ci/gate.py`:** `evaluate()` and `render()`. `allow_incomplete` already exists and
  must keep its meaning.
- **`tools/security-ci/src/security_ci/cli.py`:** `--allow-incomplete`, unchanged.

Required behaviour (design section 21, Q4):

- **`native_verification`:** read the report's `native_verification` block. A native INCOMPLETE is an incomplete input:
  add an entry mentioning `native` to `bundle.incomplete`.
  - The default gate then fails.
  - `--allow-incomplete` is only an explicit opt-out: the gate passes, but the INCOMPLETE status and the "Incomplete:"
    line stay.
  - It never turns INCOMPLETE into PASS. `test_allow_incomplete_is_only_an_opt_out` and
    `test_incomplete_area_status_never_becomes_pass` already pin this for the import path.
- **`nativeVerification`:** Phase 3 run property `{"status", "requestsCount"}` taken from `native_verification`.
- **`origin`:** findings whose report `source` is `native-verification` get result property
  `origin: "native-verification"`.
- **Source properties:** run properties `verificationSource` (the report's aggregate Authorization source) and
  `verificationSubareaSource` (per sub-area), carried from the Phase 3 report's `authorization.verification_source`
  / `verification_subarea_source`.
- **`mixed`:** invalid as an individual sub-area source; that sub-area's status becomes INCOMPLETE.
- **Boundaries:** security-ci only reads report JSON. It executes nothing and makes no network requests. Redaction
  in `security_ci/redaction.py` stays in force: `test_planted_secrets_absent_from_sarif_and_gate_output` must keep
  passing.

## 7. v1.2 Compatibility Requirements

Preserve:

- **Imported-result behaviour** (`verification_results`, schema 1.0): all-or-nothing validation, request budget 20,
  namespaces, credential-field rejection, value redaction and status rules. The report fields keep their meaning:
  `verification_import`, `source: imported`, `requests_count`, `limitations`, `evidence`.
- **Status semantics:** `verification/status.py`, `resolve()` and `aggregate()`.
- **Namespaces:** `RT-AUTH`, `RT-SESSION`, `RT-AUTHZ`, `RT-IDOR`, `RT-TENANT`, and the Phase 3A and ZAP namespaces.
- **Malformed input:** malformed or invalid imports make the import INCOMPLETE. Malformed reports are rejected by the
  reader (`ValueError`) and by security-ci (`InputError`, CLI exit 3).
- **Tests:** all existing v1.2 tests pass unmodified, including `test_verification_import.py`,
  `test_verification_status.py`, `test_authz_subareas.py`, `test_imported_verification.py` and the passing tests in
  `test_v13_import_regression.py` and `test_v13_native_reports.py`.
- **Releases:** released tags (`v1.2.0`, `quality-ci-v1.2`, `engineering-ci-v1.2`, earlier tags) and the released
  v1.2 implementation are not modified.

v1.3 reporting changes must stay backward-compatible with old imported reports. A v1.2 report without the new fields
must still be read by the reader and security-ci with the same results.

## 12. Handoff Notes

- **The tests are the contract:** the acceptance tests and the design define the required behaviour.
- **No new internal APIs:** do not invent internal APIs to satisfy tests. The v1.3 tests deliberately use existing
  public boundaries: the JSON report, the reader script, security-ci `load_all`/`build`/`evaluate`/CLI, and the
  workflow's Combined result script.
- **Keep v1.2 compatible:** old reports and imports must behave exactly as before.
- **No shortcuts to green CI:** do not turn an xfail into a skip, loosen an assertion, or delete a test.
- **No verification claims without evidence:** do not describe native Authentication, Session, Authorization,
  IDOR/BOLA or tenant-isolation behaviour as verified until native execution exists and produces evidence. Until
  then those areas are imported (validated, not independently proven by Vibe-Code) or NOT VERIFIED.
